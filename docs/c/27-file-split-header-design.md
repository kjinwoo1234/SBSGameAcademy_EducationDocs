# Chapter 27 파일 분할과 헤더파일 디자인

## 학습 목표

- `.c` 구현과 `.h` 선언으로 역할을 나누는 이유를 이해한다.
- include guard로 헤더 중복 포함을 막고, 다중 파일 컴파일·링크 흐름을 익힌다.
- 파일 단위 `static`으로 이름을 파일 안에 가두는 방법을 안다.

## 본문

### 27-1 왜 파일을 나누는가

프로그램이 커지면 `main` 하나에 모든 함수를 넣기 어렵습니다. **기능별 `.c` 파일**로 나누면 역할이 분명해지고, 여러 사람이 다른 파일을 고치기 쉽습니다. 바깥에 공개할 약속은 **헤더 `.h`**에 두고, 실제 코드는 `.c`에 둡니다.

전형 예는 `main.c`가 시작점, `calc.c`가 계산 구현, `calc.h`가 `add` 같은 선언입니다. 다른 파일이 계산을 쓰려면 `#include "calc.h"`만 하면 됩니다.

| 파일 | 역할 |
|---|---|
| `*.h` | 선언. 인터페이스 |
| `*.c` | 정의. 실제 동작 |
| `main.c` | 프로그램 시작·조합 |

**인터페이스**는 다른 파일이 호출할 수 있게 밖에 내놓은 함수·타입 선언입니다.

### 27-2 헤더와 include guard

헤더에는 함수 **원형**, `struct`/`typedef`, 공개 매크로 정도를 둡니다. 함수 **본체**나 전역 변수 정의를 헤더에 두면, 여러 `.c`가 그 헤더를 포함할 때 **중복 정의** 오류가 나기 쉽습니다.

같은 헤더가 간접 include로 두 번 들어오면 선언이 반복될 수 있습니다. **include guard**는 이를 막습니다.

```c
#ifndef CALC_H
#define CALC_H
/* 선언들 */
#endif
```

처음 포함될 때 `CALC_H`를 정의하고, 두 번째부터는 `#ifndef`가 실패해 안쪽을 건너뜁니다. 가드 이름은 파일마다 다르게 짓습니다.

아래 세 파일이 한 프로젝트라고 보고, 빌드 후 출력을 확인하세요.

```c
/* calc.h */
#ifndef CALC_H
#define CALC_H

int add(int a, int b);

#endif
```

```c
/* calc.c */
#include "calc.h"

int add(int a, int b)
{
    return a + b;
}
```

```c
/* main.c */
#include <stdio.h>
#include "calc.h"

int main(void)
{
    printf("3 + 4 = %d\n", add(3, 4));
    return 0;
}
```

**예상 출력**

```text
3 + 4 = 7
```

**코드 해석**

- `calc.h`는 `add` 선언만 둡니다.
- `calc.c`가 정의를 갖고, `main.c`는 헤더만 include해 호출합니다.
- 가드 `CALC_H`가 중복 포함을 막습니다.

빌드 예는 환경에 따라 `gcc main.c calc.c -o app`처럼 **모든 `.c`를 함께** 컴파일·링크하는 형태입니다. IDE면 프로젝트에 두 소스를 넣고 빌드합니다.

### 27-3 컴파일과 링크

각 `.c`는 보통 **따로 컴파일**되어 목적 파일이 되고, **링크** 단계에서 심볼을 이어 실행 파일을 만듭니다. `main`이 `add`를 호출할 수 있는 것은 링크가 `calc.c` 쪽 정의를 찾아 주기 때문입니다. 선언만 있고 정의가 있는 `.c`를 빼먹으면 링크 오류가 납니다.

헤더를 include했다고 구현이 자동으로 들어오지는 않습니다. **선언은 헤더, 정의는 어떤 `.c`, 빌드에는 그 `.c` 포함**이 한 세트입니다.

| 단계 | 하는 일 |
|---|---|
| 컴파일 | `.c` → 목적 파일 |
| 링크 | 목적 파일들을 실행 파일로 결합 |

### 27-4 `static`으로 파일 안에 가두기

함수나 전역 변수 앞에 **`static`**을 붙이면 **그 `.c` 파일 안에서만** 보입니다. 다른 파일이 같은 이름 함수를 만들어도 링크 충돌이 나지 않습니다. 헬퍼처럼 바깥에 공개할 필요 없는 함수에 씁니다.

헤더에 원형을 올리지 않으면 다른 파일이 호출할 수도 없습니다. 공개 API만 헤더에 두고, 나머지는 `static`으로 숨기는 구성이 흔합니다.

아래는 개념 확인용입니다. `helper`는 `calc.c` 안에서만 쓰입니다.

```c
/* calc.c 일부 예시 */
#include "calc.h"

static int clamp_nonneg(int x)
{
    if (x < 0)
    {
        return 0;
    }
    return x;
}

int add(int a, int b)
{
    return clamp_nonneg(a) + clamp_nonneg(b);
}
```

**코드 해석**

- `clamp_nonneg`는 `static`이라 다른 `.c`에서 링크되지 않습니다.
- `add`만 헤더로 공개합니다.
- 내부 세부 구현을 파일 안에 가둡니다.

### 27-5 헤더 디자인 습관

권장 습관은 다음과 같습니다. 헤더에는 선언만 둡니다. 가드를 붙입니다. 표준 헤더가 필요하면 헤더 안에서도 `#include <stdio.h>`처럼 최소만 넣습니다. 순환 include는 피합니다. A가 B를 필요로 하면 전방 선언으로 충분한지 먼저 봅니다.

학습용 작은 프로젝트는 `util.h` / `util.c` / `main.c` 세 장이면 충분합니다. 다음 장 콘솔 게임도 유틸 헤더를 같은 방식으로 나눕니다.

### 연습문제

**문제 1**
- 문제: `sub`와 `mul`을 `calc.h`에 선언하고 `calc.c`에 정의한 뒤, `main`에서 `add`·`sub`·`mul` 결과를 출력하세요.
- 입력: 없음. 피연산자 `8`, `2`를 코드에 넣어도 됨
- 출력:
  ```text
  10
  6
  16
  ```
- 조건: 헤더에는 선언만. include guard 유지

**문제 2**
- 문제: `main.c`와 `calc.c`를 한 실행 파일로 빌드해 문제 1 출력이 나오게 하세요.
- 입력: 소스 2개 + 헤더 1개
- 출력: 위와 동일
- 조건: 링크 오류 없이 실행. 헤더만 넣고 `calc.c`를 빼먹지 말 것

**문제 3**
- 문제: `calc.c`에만 보이는 `static int abs_int(int x)`를 두고, 공개 함수 `int distance(int a, int b)`가 `|a - b|`를 반환하게 하세요. `main`에서 `distance(3, 10)`을 출력하세요.
- 입력: 없음
- 출력: `7`
- 조건: `abs_int`는 헤더에 올리지 않음. `static` 사용

### 정답 포인트

- 문제 1: `int sub(int a, int b);` `int mul(int a, int b);` 선언·정의 분리 후 `main`에서 호출
- 문제 2: 빌드에 `main.c`와 `calc.c` 모두 포함
- 문제 3: `static` 헬퍼 + `distance`만 `calc.h`에 선언
- 공통: 헤더=선언, 소스=정의, 가드, 공개 최소·`static`으로 내부 숨김
