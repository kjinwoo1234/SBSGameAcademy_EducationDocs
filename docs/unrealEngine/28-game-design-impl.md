# Chapter 28 게임 기획과 구현

## 학습 목표

- 조작·규칙·피드백을 한 장짜리 기획으로 문서화할 수 있다.
- 기능을 Must·Should·Could로 나누어 구현 순서를 정할 수 있다.
- 기획에 맞춰 지금까지 만든 프로젝트에 기능을 골라 확장할 수 있다.

## 본문

### 28-1 무엇을 기획하는가

지금 프로젝트에는 이동, 근접 콤보, 총, 데미지, 처치 점수, 적 AI, 체력바가 들어 있습니다. 기능은 많지만 아직 "게임"은 아닙니다. 무엇을 하면 이기는지, 한 판이 얼마나 걸리는지, 플레이어가 어떤 재미를 느껴야 하는지가 정해지지 않았습니다.

이 장은 새 엔진 기능을 배우는 장이 아닙니다. 이미 만든 것을 하나의 게임으로 묶기 위해 범위를 정합니다. 만들 내용을 미리 글로 정리하는 일을 **기획**이라고 합니다.

최소한 아래 항목을 채웁니다.

| 항목 | 적을 내용 예 |
|---|---|
| 플레이어 조작 | 이동, 조준, 발사, 근접 공격, 재장전 여부 |
| 게임 규칙 | 목표 점수, 제한 시간, 생명 수 |
| 사운드 | 발사음, 명중음, 배경음 유무 |
| 이펙트 | 총구 화염, 명중 불꽃 |
| UI | 체력, 점수, 남은 시간 |
| 게임플레이 | 적 종류 수, 적이 나타나는 방식 |

### 28-2 우선순위 나누기

적은 것을 한 번에 다 만들 수는 없습니다. 항목마다 세 등급 중 하나를 붙입니다.

| 등급 | 의미 | 예 |
|---|---|---|
| Must | 없으면 게임이 성립하지 않는다 | 승리 조건, 적 처치, 체력 표시 |
| Should | 있으면 훨씬 좋아진다 | 발사음, 명중 이펙트 |
| Could | 시간이 남으면 넣는다 | 두 번째 무기, 적 종류 추가 |

Must만 먼저 코드로 옮깁니다. Should는 Must가 모두 동작한 뒤에, Could는 목록에만 남겨 둡니다. 하고 싶은 것을 다 적은 뒤 지우는 것이 처음부터 고르는 것보다 쉽습니다.

### 28-3 일정 세우기

Must 항목을 구현 순서대로 번호를 붙입니다. 순서를 정할 때 기준은 **각 단계가 끝날 때마다 플레이 가능한 상태가 남는가**입니다.

예를 들어 다음과 같이 적을 수 있습니다.

1. 목표 점수에 도달하면 결과 화면을 띄운다.
2. 플레이어 체력이 0이 되면 패배 화면을 띄운다.
3. 적이 일정 시간마다 새로 나타나게 한다.
4. 남은 시간을 화면에 표시하고 시간이 다 되면 끝낸다.

1번만 끝나도 "이기는 게임"이 되고, 2번이 끝나면 "질 수도 있는 게임"이 됩니다. 반대로 "UI를 전부 만든 뒤 규칙을 넣는다" 같은 순서는 중간에 실행해 볼 수 없어 문제를 늦게 발견합니다.

팀으로 작업한다면 Chapter 14의 이름 규칙과 폴더 구조를 이 시점에 함께 정합니다.

### 28-4 컴포넌트로 나누어 구현

기능을 캐릭터 클래스 하나에 모두 넣으면 파일이 길어지고, 같은 기능을 적이나 상자에도 넣고 싶을 때 다시 쓸 수 없습니다. Chapter 15에서 배운 대로 액터의 일은 컴포넌트가 하므로, 기능을 컴포넌트로 나눕니다.

| 컴포넌트 | 맡는 일 | 붙일 수 있는 액터 |
|---|---|---|
| 체력 컴포넌트 | 체력 값, 피해와 회복, 사망 알림 | 플레이어, 적, 부서지는 상자 |
| 무기 컴포넌트 | 발사, 탄약, 재장전 | 플레이어, 포탑 |

구현할 때는 다음 순서를 따릅니다.

1. 규칙에 필요한 데이터를 먼저 정한다. 예: 목표 점수, 최대 체력.
2. 데이터가 바뀌는 코드 경로를 연결한다. 예: 처치하면 점수가 오른다.
3. 플레이어가 알 수 있게 피드백을 붙인다. 소리, 이펙트, UI.
4. 조작이 불편한 곳만 최소한으로 고친다.

소리는 `UGameplayStatics::PlaySoundAtLocation` 한 줄로 재생할 수 있고, 이펙트는 명중 지점에 스폰합니다. 체력 컴포넌트와 소리·이펙트의 실제 코드는 Chapter 29에서 다룹니다.

### 28-5 따라하기 — 기획서와 Must 구현

1. 28-1의 표를 자신의 게임 내용으로 채운다.
2. 각 항목에 Must, Should, Could를 붙인다.
3. Must 항목에 구현 순서 번호를 붙인다. 번호마다 "이 단계가 끝나면 무엇을 플레이해 볼 수 있는가"를 한 줄로 적는다.
4. Must 1번을 구현해 플레이 가능한 상태를 만든다. Chapter 22의 게임모드 규칙을 고치는 것부터 시작한다.
5. 구현하면서 생각난 추가 아이디어는 코드에 넣지 말고 Could 목록에 적는다.

이 장의 결과물은 한 장짜리 기획서와 Must 1번이 동작하는 프로젝트입니다.

### 연습문제

1. 문제: 자신의 게임에서 Must 항목 세 개를 목록으로 쓰세요.  
   - 조건: 승리 또는 패배 조건을 하나 이상 포함할 것
2. 문제: Could로 미룬 기능 하나를 고르고 미룬 이유를 한 문장으로 쓰세요.
3. 문제: 단계마다 플레이 가능한 상태를 남기는 것이 중요한 이유를 한 문장으로 쓰세요.

### 정답 포인트

- Must는 규칙·조작·최소 피드백. Could는 없어도 게임이 성립하는 장식이나 추가 콘텐츠. 중간에 실행해 볼 수 있어야 문제를 일찍 발견한다.
