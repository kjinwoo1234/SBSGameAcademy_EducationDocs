# Chapter 30 멀티플레이 기초

## 학습 목표

- 클라이언트-서버 모델에서 서버와 클라이언트가 각각 맡는 일을 설명할 수 있다.
- 네 가지 네트워크 모드를 구분하고 에디터에서 여러 명으로 플레이해 볼 수 있다.
- Server·Client·Multicast RPC와 오너십의 관계를 구분해 설명할 수 있다.
- 리플리케이션이 RPC와 어떻게 다른지 설명할 수 있다.

## 본문

### 30-1 클라이언트-서버 모델

지금까지 만든 게임은 컴퓨터 한 대에서 혼자 플레이했습니다. 여러 사람이 각자의 컴퓨터로 같은 게임 세상에 들어오려면, 누가 어디에 있고 누구의 체력이 얼마인지를 모든 컴퓨터가 똑같이 알아야 합니다.

컴퓨터마다 따로 계산하면 결과가 어긋납니다. 내 화면에서는 적을 맞혔는데 상대 화면에서는 빗나간 일이 생깁니다. 그래서 언리얼은 한 대를 기준으로 정하는 **클라이언트-서버 모델**을 씁니다.

| 역할 | 하는 일 |
|---|---|
| 서버 | 게임이 실제로 진행되는 곳. 모든 판정의 기준이 된다 |
| 클라이언트 | 서버에 접속한 플레이어의 컴퓨터. 입력을 서버에 보내고 서버가 알려 준 결과를 화면에 그린다 |

서버는 화면 영상을 보내 주지 않습니다. "이 액터가 여기 있고 이 변수 값이 얼마다"라는 정보만 보내고, 각 클라이언트가 그 정보로 자기 화면에 같은 장면을 만들어 냅니다.

데미지와 점수처럼 중요한 판정은 서버에서만 합니다. 클라이언트가 "내가 맞혔다"고 정할 수 있게 두면 조작된 프로그램으로 쉽게 속일 수 있습니다. 판정의 최종 권한을 **오소리티**라고 하고, 보통 서버가 가집니다.

### 30-2 네트워크 모드

실행 중인 게임 프로그램 하나가 네트워크에서 어떤 위치에 있는지를 **네트워크 모드**라고 합니다.

| 모드 | 설명 |
|---|---|
| 스탠드얼론 | 혼자 플레이한다. 지금까지의 방식 |
| 데디케이티드 서버 | 서버 역할만 한다. 화면도 플레이어도 없다 |
| 리슨 서버 | 서버이면서 그 컴퓨터의 주인도 플레이어로 참가한다 |
| 클라이언트 | 서버에 접속한 참가자 |

**리슨 서버**는 친구끼리 방을 만들어 하는 게임에 쓰고, **데디케이티드 서버**는 회사가 서버 컴퓨터를 운영하는 게임에 씁니다. 방을 만든 사람을 **호스트**라고 부릅니다. 이 과정에서는 리슨 서버로 실습합니다.

### 30-3 에디터에서 여러 명으로 플레이하기

컴퓨터가 한 대뿐이어도 에디터가 창을 여러 개 띄워 멀티플레이를 흉내 내 줍니다. 패키징하지 않고 에디터 안에서 바로 플레이하는 것을 줄여서 **PIE**라고 부르며, 뒤 장에서 이 말을 계속 씁니다.

1. 툴바의 재생 버튼 옆 점 세 개 메뉴를 연다.
2. **플레이어 수**를 `2`로 바꾼다.
3. **넷 모드**를 **리슨 서버로 플레이**로 바꾼다.
4. 재생 버튼을 누른다.

![에디터 플레이 설정 메뉴: 플레이어 수 2, 넷 모드가 리슨 서버로 플레이로 선택된 화면](./img/30-pie-listen-server-settings.png)

창이 두 개 뜹니다. 하나는 호스트이고 다른 하나는 클라이언트입니다. 창 제목에 `Server` 또는 `Client`가 표시됩니다.

![창 두 개가 떠서 호스트와 클라이언트가 같은 레벨을 플레이하는 화면](./img/30-pie-two-windows.png)

템플릿 캐릭터는 이동이 서로의 창에 보입니다. 캐릭터 무브먼트가 이동 동기화를 이미 지원하기 때문입니다. 하지만 Part 02와 03에서 직접 만든 공격, 체력, 점수는 쏜 창에서만 반응합니다. 이 Part에서 그것들을 하나씩 네트워크에 맞게 고칩니다.

### 30-4 리플리케이션

서버의 상태를 클라이언트에 그대로 재현하는 일을 **리플리케이션**이라고 합니다. 복제라고도 부릅니다.

액터는 기본적으로 복제되지 않습니다. 서버에서 액터를 스폰해도 클라이언트 화면에는 나타나지 않습니다. 복제를 켜야 합니다.

| 켜는 곳 | 방법 |
|---|---|
| C++ | 생성자에서 `bReplicates = true;` |
| 블루프린트 | 클래스 디폴트의 **리플리케이트**에 체크 |

복제가 켜진 액터 안에서, 값이 서버와 같게 유지되어야 하는 변수에는 표시를 붙입니다.

```cpp
// 헤더
UPROPERTY(Replicated)
int32 Ammo;

virtual void GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& OutLifetimeProps) const override;
```

```cpp
// 소스
#include "Net/UnrealNetwork.h"

void AMyCharacter::GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& OutLifetimeProps) const
{
	Super::GetLifetimeReplicatedProps(OutLifetimeProps);
	DOREPLIFETIME(AMyCharacter, Ammo);
}
```

**코드 해석**

- `UPROPERTY(Replicated)`는 이 변수를 복제 대상으로 표시합니다.
- `GetLifetimeReplicatedProps`는 "이 클래스에서 복제할 변수 목록"을 엔진에 알려 주는 함수입니다.
- `DOREPLIFETIME(클래스, 변수)` 한 줄이 변수 하나를 목록에 등록합니다. `Replicated` 표시와 이 등록이 둘 다 있어야 복제됩니다.

서버에서 `Ammo` 값을 바꾸면 얼마 뒤 모든 클라이언트의 같은 액터에서 `Ammo`가 같은 값이 됩니다. 반대 방향은 없습니다. 클라이언트에서 값을 바꿔도 서버로 전달되지 않습니다.

### 30-5 RPC

클라이언트가 서버에게 "발사하고 싶다"고 알리려면 다른 방법이 필요합니다. 다른 컴퓨터에 있는 같은 액터의 함수를 실행해 달라고 요청하는 것을 **RPC**라고 합니다. 원격 프로시저 호출의 줄임말입니다.

| 종류 | 호출하는 쪽 | 실행되는 곳 | 예 |
|---|---|---|---|
| Server RPC | 클라이언트 | 서버 | 발사 요청, 상호작용 요청 |
| Client RPC | 서버 | 그 액터를 소유한 클라이언트 한 곳 | 그 플레이어만 보는 알림 |
| Multicast RPC | 서버 | 서버와 모든 클라이언트 | 폭발 이펙트, 소리 |

```cpp
UFUNCTION(Server, Reliable)
void Server_RequestFire();

UFUNCTION(NetMulticast, Unreliable)
void Multicast_PlayMuzzleFX();
```

`Reliable`은 반드시 전달되도록 보장합니다. `Unreliable`은 네트워크가 혼잡하면 빠질 수 있습니다. 이펙트처럼 한 번 빠져도 괜찮은 것은 `Unreliable`로 둡니다. `Reliable`을 남용하면 통신량이 늘어 지연이 커집니다.

호출할 때는 선언한 이름 `Server_RequestFire()`를 그대로 씁니다. 실행될 내용은 엔진 규칙에 따라 `Server_RequestFire_Implementation`이라는 이름의 함수에 적습니다. 구현은 Chapter 33에서 다룹니다.

리플리케이션과 RPC를 구분하는 기준은 이렇습니다.

| 도구 | 성격 | 예 |
|---|---|---|
| 리플리케이션 | 계속 같아야 하는 **상태** | 체력, 탄약, 점수 |
| RPC | 한 번 일어나는 **사건** | 발사 요청, 폭발 이펙트 재생 |

### 30-6 RPC와 오너십

액터를 어느 클라이언트의 연결이 소유하는가를 **오너십**이라고 합니다. 플레이어 컨트롤러와 그것이 빙의한 폰은 그 플레이어의 연결이 소유합니다.

Server RPC는 **자신이 소유한 액터**에서만 보낼 수 있습니다.

1. 내 캐릭터에서 `Server_RequestFire()`를 호출한다. 내 소유이므로 서버로 전달된다.
2. 남의 캐릭터나 주인 없는 액터에서 호출하면 엔진이 요청을 버린다. 아무 일도 일어나지 않는다.

Server RPC가 동작하지 않을 때 가장 먼저 의심할 것이 오너십입니다. 문이나 상자처럼 주인 없는 액터와 상호작용하려면, 내 캐릭터의 Server RPC로 "저 문을 열고 싶다"고 요청하고 서버에서 문을 열게 합니다.

서버는 요청을 그대로 믿지 않고 탄약이 있는지, 거리가 너무 멀지 않은지 같은 조건을 다시 확인합니다. 흐름은 **내 입력 → 내 소유 액터의 Server RPC → 서버가 확인하고 판정**으로 기억합니다.

### 30-7 따라하기 — 복제와 RPC 확인

1. 플레이어 수 2, 리슨 서버로 플레이해 이동이 서로 보이는지 확인한다.
2. 캐릭터에 `Replicated` 정수 변수 `Ammo`를 추가하고 `DOREPLIFETIME`으로 등록한다.
3. `Tick`에서 `PLOG`로 `Ammo` 값을 찍는다.
4. Server RPC `Server_UseAmmo`를 만들고 `_Implementation`에서 `Ammo`를 1 줄인다.
5. 키 입력에서 `Server_UseAmmo()`를 호출한다.
6. 클라이언트 창에서 키를 눌러 두 창의 로그에서 `Ammo`가 함께 줄어드는지 확인한다.
7. Server RPC를 거치지 않고 클라이언트에서 직접 `Ammo`를 줄이게 바꿔 보고, 서버 창의 값이 바뀌지 않는 것을 확인한 뒤 되돌린다.

방을 만들고 참가하는 방법은 Chapter 31, 체력 동기화는 Chapter 32에서 다룹니다.

### 연습문제

1. 문제: 데미지 판정을 클라이언트에서 하게 두면 생기는 문제를 한 문장으로 쓰세요.
2. 문제: 체력 값과 폭발 이펙트 재생에 각각 리플리케이션과 RPC 중 무엇이 어울리는지 쓰고 이유를 한 줄씩 쓰세요.
3. 문제: 레벨에 놓인 문 액터에서 Server RPC를 호출했는데 서버에서 실행되지 않는 이유를 한 문장으로 쓰세요.  
   - 조건: 오너십을 언급할 것

### 정답 포인트

- 조작으로 속이기 쉽고 컴퓨터마다 결과가 어긋난다. 체력은 계속 같아야 하는 상태라 리플리케이션, 폭발은 한 번 일어나는 사건이라 Multicast RPC. 문은 그 클라이언트가 소유한 액터가 아니라서 요청이 버려진다.
