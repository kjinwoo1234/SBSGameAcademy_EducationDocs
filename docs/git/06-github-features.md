# Chapter 6 GitHub 100% 활용하기

## 학습 목표
- 프로필·README로 자기 소개 저장소를 꾸민다.
- 리뷰하기 좋은 PR 작성 습관을 적용한다.
- 브랜치 보호 규칙의 목적을 설명한다.

## 본문

<a id="ch6-1"></a>
### 6-1 GitHub 프로필 꾸미기

GitHub 프로필은 저장소 목록만 보이는 화면이 아닙니다. **프로필 README**는 사용자명과 **같은 이름**의 저장소에 둔 `README.md`가 프로필 상단에 보여지는 소개 문서입니다. 예를 들어 사용자명이 `octocat`이면 `octocat/octocat` 저장소의 `README.md`가 프로필에 표시됩니다.

**핀(pin)**은 프로필에 대표 저장소를 최대 6개까지 고정해 두는 기능입니다. 방문자가 먼저 볼 프로젝트를 직접 고를 때 씁니다.

아래 순서로 프로필 README를 한 번 만들어 보세요.

1. GitHub에서 사용자명과 **동일한 이름**의 공개 저장소를 만듭니다.
2. 저장소 루트에 `README.md`를 두고 짧은 자기소개를 적습니다.
3. 프로필 페이지를 새로고침해 소개가 보이는지 확인합니다.
4. 프로필의 Customize pins에서 대표 저장소를 고릅니다.

**절차 해석**
- 1~2단계는 “특수 이름 저장소 + README”가 프로필 소개의 조건임을 확인합니다.
- 3단계는 웹에 반영됐는지 보는 검증입니다.
- 4단계는 핀으로 대표작을 고르는 단계입니다.

<a id="ch6-2"></a>
### 6-2 더 좋은 풀 리퀘스트 만들기

앞 장에서 PR은 리뷰·토론 뒤 병합하는 절차라고 배웠습니다. 이 장에서는 **리뷰하기 좋은 글쓰기**에 초점을 둡니다. 제목은 변경의 **한 줄 요약**이고, 동사로 시작하면 무엇이 바뀌는지 빠르게 읽힙니다. 본문에는 **배경**, 필요하면 **스크린샷**, **재현·확인 절차**, **리스크**, **체크리스트**를 적습니다. 변경 범위가 작을수록 리뷰 속도와 품질이 좋아지는 경우가 많습니다.

아래 표를 읽고, 같은 변경이라도 어떤 제목·본문이 리뷰에 도움이 되는지 비교해 보세요.

| 나쁜 예 | 좋은 예 |
|---------|---------|
| "수정" | "Fix null crash when user logs out" |
| 변경 파일만 나열 | 왜 바꿨는지 + 테스트 방법 |

**표 해석**
- 왼쪽은 리뷰어가 의도를 추측해야 해서 질문이 늘어납니다.
- 오른쪽은 목적과 확인 방법이 보여 승인·수정 요청이 빨라집니다.

<a id="ch6-3"></a>
### 6-3 GitHub에서 풀 리퀘스트 되돌리기

앞 장에서 `revert`는 **되돌리는 새 커밋**을 만든다고 배웠습니다. GitHub 웹에서도 비슷한 일을 할 수 있습니다. 이미 병합된 PR 화면의 **Revert**를 누르면, 그 병합을 되돌리는 **새 PR**이 만들어집니다. 이력을 지우는 것이 아니라, 반대 변경을 다시 리뷰·병합하는 방식입니다.

연습용 저장소에서 아래를 따라 해 보세요. 실무 `main`에서는 팀 규칙에 맞게 진행합니다.

1. 이미 병합된 PR 페이지를 엽니다.
2. **Revert**를 눌러 되돌리기용 새 PR이 생기는지 확인합니다.
3. 새 PR 설명에 “왜 되돌리는지”를 짧게 적고, 리뷰 후 병합합니다.

**절차 해석**
- Revert는 과거 커밋을 삭제하지 않고, 되돌림용 변경을 **새 PR**로 남깁니다.
- 그래서 감사·추적이 필요한 공유 브랜치에서 UI Revert가 입문에 익숙합니다.
- CLI로 병합 커밋을 되돌리는 옵션은 이후 CLI 장에서 필요할 때 다룹니다.

<a id="ch6-4"></a>
### 6-4 브랜치 보호하기

**Branch protection**(브랜치 보호)은 `main`처럼 중요한 브랜치에 규칙을 걸어, 실수로 직접 덮어쓰는 일을 줄이는 설정입니다. 대표적으로 **직접 푸시 금지**, **PR 필수**, **리뷰 승인**, **CI 통과**를 강제할 수 있습니다.

저장소에서 아래 경로로 규칙을 확인해 보세요.

1. 저장소 **Settings** → **Branches**로 이동합니다.
2. **Branch protection rules**에서 `main` 규칙을 추가하거나 엽니다.
3. Require a pull request before merging 같은 항목이 무엇인지 읽고, 연습 저장소라면 켜 둡니다.

**절차 해석**
- 보호 규칙은 “누가 `main`에 어떻게 합류하는지”를 저장소가 강제하는 장치입니다.
- PR 필수를 켜면 개인 습관이 아니라 **저장소 정책**으로 리뷰 경로가 고정됩니다.

이 장 범위는 프로필·좋은 PR·웹 Revert·브랜치 보호입니다. 이슈·마일스톤·Projects 운영과 팀 브랜치 전략 이름은 이후 장에서 이어갑니다.

### 연습문제

**문제 1**
- 문제: 브랜치 보호에서 "Require pull request before merging"을 켜면 팀 워크플로가 어떻게 바뀌는지 두 문장 이상으로 설명하세요.
- 입력: 없음. 본문 6-4를 근거로 서술
- 출력: `main` 직접 푸시 대신 PR을 거쳐야 한다는 점과, 리뷰·논의가 병합 전에 들어온다는 점이 드러난 설명
- 조건: “편해진다”만 쓰지 말고, 푸시·PR·병합 관계를 포함

**문제 2**
- 문제: 병합된 PR을 웹에서 Revert했을 때 저장소 이력에 남는 것은 무엇인지 고르고 이유를 쓰세요. (A) 해당 병합 커밋이 삭제됨 (B) 되돌리는 변경을 담은 새 PR·커밋이 생김
- 입력: 없음
- 출력: 정답 기호와 한 줄 이유
- 조건: 본문 6-3 기준

**문제 3**
- 문제: 사용자명이 `mina`일 때 프로필 README가 보이려면 어떤 저장소에 `README.md`를 두어야 하는지 경로 형태로 쓰세요.
- 입력: 사용자명 `mina`
- 출력: `mina/mina` (또는 동등한 저장소 경로 표기)
- 조건: 본문 6-1의 “동일 이름 저장소” 규칙만 사용

### 정답 포인트
- 문제 1: 보호 규칙이 켜지면 `main`에 바로 푸시해 합류하지 못하고, 변경은 PR로 들어온 뒤 리뷰·병합한다.
- 문제 2: (B). Revert는 이력을 지우는 삭제가 아니라 되돌림용 **새 PR**을 만든다.
- 문제 3: `mina/mina` 저장소의 `README.md`가 프로필에 표시된다.
