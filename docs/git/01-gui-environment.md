# Chapter 1 GUI를 위한 버전 관리 환경 구축하기

## 학습 목표

- SourceTree와 Visual Studio Code를 설치하고 기본 설정을 마친다.
- GitHub 웹 UI에서 저장소·이슈·PR 화면의 역할을 구분한다.

## 본문

<a id="ch1-1"></a>

### 1-1 소스트리 설치하기

**SourceTree**는 Atlassian에서 제공하는 **Git GUI 클라이언트**입니다. 명령어 대신 클릭으로 커밋·푸시·브랜치를 다룰 수 있습니다.

| 용어 | 의미 |
|------|------|
| GUI | Graphical User Interface. 마우스·화면 중심 인터페이스 |

아래 순서로 SourceTree를 설치하고 첫 화면까지 열어 보세요.

1. SourceTree 설치 파일을 받아 실행합니다.
2. 설치 마법사에서 **내장 Git** 또는 **시스템 Git** 중 하나를 고릅니다. 이미 Git for Windows를 썼다면 시스템 Git을 지정해도 됩니다.
3. 첫 실행에서 계정 연동을 물으면, 교육용으로 계정 없이 진행 가능한 옵션이 있으면 그 경로를 따릅니다. 없으면 안내에 따라 계정을 연결합니다.
4. 시작 화면에서 **Local** 또는 저장소 목록이 보이는지 확인합니다.

예상 결과:

```text
SourceTree 창이 열리고, 로컬/원격 저장소를 추가할 수 있는 시작 화면이 보인다.
```

**절차 해석.** GUI는 Git의 작업 트리 → 스테이징 → 커밋 개념을 화면으로 보여 줍니다. 실제 커밋·푸시 연습은 [Chapter 2](./02-solo-sourcetree.md)에서 이어집니다.

### 1-2 비주얼 스튜디오 코드 설치하기

**Visual Studio Code(VS Code)**는 편집기이며, **내장 Git 뷰**로 diff 확인·스테이징·커밋·푸시를 할 수 있습니다.

아래 순서로 VS Code를 설치하고 Git 뷰를 확인해 보세요.

1. VS Code를 설치한 뒤 실행합니다.
2. **파일 → 폴더 열기**로 Chapter 0에서 만든 저장소 폴더 또는 빈 연습 폴더를 엽니다.
3. 왼쪽 **소스 제어** 아이콘을 눌러 Git 패널이 열리는지 확인합니다.
4. 필요하면 확장에서 **GitHub Pull Requests**를 검색해 설치합니다. PR 검토는 이후 장에서 사용합니다.
5. 메뉴 **터미널 → 새 터미널**로 편집기 안 터미널을 엽니다.

예상 결과:

```text
소스 제어 패널에 변경 파일 목록 또는 "저장소를 초기화" 안내가 보인다.
하단 또는 옆 패널에 터미널이 열린다.
```

**절차 해석.** 편집·검색·Git이 한 화면에 모이면 CLI와 GUI를 섞어 쓰기 쉽습니다. 스테이징·커밋 자체는 Chapter 2와 같은 흐름입니다.

### 1-3 GitHub 둘러보기

GitHub 저장소 페이지의 탭은 역할이 다릅니다.

| 탭 | 주 용도 |
|----|---------|
| Code | 파일 트리, 브랜치 전환, 최근 커밋 요약 |
| Issues | 할 일·버그·토론을 이슈로 관리 |
| Pull requests | 브랜치 병합 전 **코드 리뷰**와 대화 |
| Actions | CI/CD 워크플로. 자동 빌드·테스트 |
| Settings | 브랜치 보호, 시크릿, 협업자 |

**PR**은 **Pull Request**의 약자입니다. 한국어로는 풀 리퀘스트 또는 병합 요청이라고 부르며, 내 브랜치의 변경을 원본에 합쳐 달라고 요청하는 협업 절차입니다. 이슈·PR을 깊게 쓰는 법은 [Chapter 15](./15-github-issues.md)·[Chapter 3](./03-collaboration-sourcetree.md)에서 이어집니다.

본인 또는 공개 저장소 하나를 연 뒤, 아래 순서로 탭을 눌러 역할을 확인해 보세요.

1. **Code** 탭에서 파일 목록과 기본 브랜치 이름을 확인합니다.
2. **Issues** 탭을 열어 열린 이슈 목록 또는 빈 목록을 확인합니다.
3. **Pull requests** 탭을 열어 열린 PR이 있으면 하나를 고릅니다.
4. PR이 있으면 **Conversation**과 **Files changed**를 각각 열어 봅니다.

예상 결과:

```text
Code에서는 파일이, Issues에서는 작업 목록이, Pull requests에서는 병합 요청 목록이 보인다.
PR을 열면 Conversation에는 대화·체크가, Files changed에는 diff가 보인다.
```

**절차 해석.** Code는 코드 자체, Issues는 할 일 기록, PR은 변경 제안·리뷰·병합을 한곳에서 다룹니다.

### 연습문제

1. 문제: SourceTree의 파일 상태 화면에서 스테이징 영역이 무엇을 의미하는지 자신의 말로 설명하세요.
   - 입력: 없음
   - 출력: 스테이징이 "다음 커밋에 넣을 변경을 모은 영역"임을 나타내는 문장
   - 조건: Chapter 0의 스테이징 개념과 모순되지 않게 쓸 것

2. 문제: VS Code에서 폴더를 연 뒤 소스 제어에서 변경 파일 1개를 스테이징하고 커밋까지 하세요.
   - 입력: 수정한 파일 1개 이상
   - 출력: 소스 제어에 커밋할 변경이 없고, 히스토리에 새 커밋이 보임
   - 조건: 커밋 메시지에 변경 요약을 넣을 것

3. 문제: 임의 오픈소스 저장소에서 열린 PR 1개를 열고, Conversation과 Files changed의 차이를 설명하세요.
   - 입력: 공개 저장소의 열린 PR 1개
   - 출력: Conversation=대화·검토, Files changed=코드 차이 요지의 두 문장
   - 조건: 실제로 두 탭을 연 뒤 작성할 것

### 정답 포인트

1. GUI의 스테이징도 Git과 같이 다음 커밋에 넣을 변경을 모아 두는 영역이다.
2. 소스 제어에서 Stage → 메시지 입력 → Commit 순이면 CLI의 `add`/`commit`과 같다.
3. PR은 변경 제안·리뷰·병합을 한곳에서 다루며, Conversation은 대화, Files changed는 diff다.
