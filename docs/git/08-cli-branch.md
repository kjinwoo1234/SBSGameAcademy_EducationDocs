# Chapter 8 CLI 환경에서 브랜치 생성 및 조작하기

## 학습 목표
- CLI로 브랜치를 생성·삭제·전환한다.
- 3-way merge 상황을 설명한다.
- 리베이스와 병합의 트레이드오프를 말로 정리한다.
- **태그**가 브랜치와 어떻게 다른지 말하고, 주석 태그를 만들어 **원격에 공유**하는 흐름을 말한다.

## 본문

<a id="ch8-1"></a>
### 8-1 브랜치 생성하기

기능이나 실험을 **기본 브랜치와 분리된 줄기**에서 진행하려면 새 브랜치를 만듭니다. 최근 Git은 **`git switch -c`**로 “만들고 바로 이동”하는 방식이 흔합니다. `-c`는 create, 즉 새 이름을 만들라는 옵션입니다. 예전 방식처럼 `git branch`로 만든 뒤 `git switch`로 이동해도 결과는 같습니다.

연습 저장소에서 아래를 실행해 보세요.

```bash
git switch -c feature/cli-demo
```

**예상 출력**

```text
Switched to a new branch 'feature/cli-demo'
```

같은 일을 두 줄로 하려면 아래처럼 합니다.

```bash
git branch feature/cli-demo
git switch feature/cli-demo
```

**명령 해석**
- `git switch -c 이름` — 브랜치를 만들고 그쪽으로 이동합니다.
- `git branch 이름` 후 `git switch 이름` — 만들기와 이동을 나눈 형태입니다.

---

<a id="ch8-2"></a>
### 8-2 브랜치 기본 조작하기

목록·삭제·원격 추적 브랜치도 CLI로 다룹니다. `git branch`는 로컬 브랜치 목록입니다. `git branch -d feature/foo`의 `-d`는 **이미 병합된** 브랜치를 지울 때 쓰는 안전한 삭제입니다. 원격에만 있는 브랜치를 받아 작업하려면 `git switch -c feature/foo origin/feature/foo`처럼 **추적 브랜치**를 만듭니다.

아래를 실행해 목록을 확인해 보세요.

```bash
git branch
```

**예상 출력**

```text
* feature/cli-demo
  main
```

**명령 해석**
- `*`가 붙은 줄이 **지금 작업 중인** 브랜치입니다.
- 병합이 끝난 기능 브랜치는 `git branch -d 이름`으로 정리합니다.

---

<a id="ch8-3"></a>
### 8-3 3-way 병합하기

**병합(merge)**은 한 브랜치의 이력을 다른 브랜치에 합치는 동작입니다. 합치는 방식은 크게 두 가지입니다.

**Fast-forward**는 대상 브랜치에 **갈라진 새 커밋이 없을 때** 포인터만 앞으로 옮기는 병합입니다. 예를 들어 `main`이 멈춘 동안 `feature`만 앞으로 갔다면, `main`을 `feature` 끝으로 밀면 됩니다.

**3-way merge**는 양쪽 브랜치가 각자 커밋을 쌓아 **갈래가 생긴 뒤**에 씁니다. Git은 **양쪽 끝 커밋**과 **공통 조상** 세 지점을 기준으로 자동 병합합니다. **공통 조상**은 두 브랜치가 갈라지기 직전의 같은 커밋입니다. 충돌이 나면 파일 안에 충돌 마커가 남고, 앞 장에서 배운 것처럼 수동으로 정리한 뒤 커밋합니다.

| 상황 | 병합 형태 |
|------|-----------|
| 한쪽만 앞으로 감, 다른 쪽은 갈래 커밋 없음 | Fast-forward 가능 |
| 양쪽 모두 새 커밋이 있음 | 3-way merge, 병합 커밋이 생길 수 있음 |

`main`에 `feature/cli-demo`를 합칠 때 아래를 따라 해 보세요.

```bash
git switch main
git merge feature/cli-demo
```

**명령 해석**
- `git switch main` — 합칠 **받는쪽** 브랜치로 이동합니다.
- `git merge feature/cli-demo` — 기능 브랜치를 `main`에 합칩니다. 갈래가 없으면 fast-forward, 있으면 3-way로 진행합니다.

<a id="ch8-4"></a>
### 8-4 리베이스하기

`git rebase main`은 현재 브랜치의 커밋들을 **main 최신 위**로 다시 쌓아 **선형에 가까운 이력**을 만듭니다. 충돌이 나면 `git rebase --continue`로 이어가고, 중단하려면 `git rebase --abort`를 씁니다. 이미 팀원과 공유한 브랜치에 무심코 rebase하면 이력이 엇갈릴 수 있으므로 팀 규칙을 따릅니다.

아래 표로 병합과 리베이스를 비교해 보세요.

| | 병합 `merge` | 리베이스 `rebase` |
|--|--------------|-------------------|
| 이력 모양 | 갈래·병합 커밋이 남을 수 있음 | 한 줄에 가깝게 다시 쌓음 |
| 언제 쓰기 좋은가 | 공유 `main`에 합칠 때 흔함 | 아직 개인인 기능 브랜치를 최신에 맞출 때 |
| 주의 | 충돌 시 마커 정리 | 이미 push한 공유 브랜치에서는 팀 규칙 확인 |

기능 브랜치에서 `main`을 최신으로 맞출 때 아래를 연습 저장소에서만 실행해 보세요.

```bash
git switch feature/cli-demo
git rebase main
```

**명령 해석**
- 현재 브랜치 커밋이 `main` 끝 위로 다시 적용됩니다.
- 팀 규칙이 “`main`에는 merge commit만”이면, rebase는 보통 **아직 공유하지 않은 기능 브랜치**에서 `main`을 따라잡을 때 씁니다.

<a id="ch8-5"></a>
### 8-5 태그로 릴리즈 지점 남기기

**태그**는 커밋 그래프에서 **특정 커밋 하나를 가리키는 이름 붙은 포인터**입니다. 브랜치는 새 커밋이 생기면 **끝을 따라 이동**하지만, 태그는 보통 출시·빌드·감사 기준처럼 “이 시점”을 **고정**해 둡니다. `v1.0.0`처럼 버전 문자열을 쓰면 커밋 해시 대신 이름으로 그 시점을 가리키기 쉽습니다.

**주석 태그**는 `git tag -a`로 만들며 메시지·작성자 정보가 들어갑니다. `-a`는 annotated, 즉 주석이 있는 태그입니다. 이름만 붙이는 **lightweight 태그**는 `git tag v1.0.0`처럼 `-a` 없이 만들 수 있으나, 팀에서는 주석 태그를 권장하는 경우가 많습니다. 원격에는 `git push origin v1.0.0`처럼 **태그 이름을 지정**해 올립니다. 여러 태그를 한꺼번에 보내려면 `git push origin --tags`를 쓰기도 합니다. 저장소 규칙·보호 설정을 따릅니다. GitHub **Releases**는 이런 태그에 빌드 산출물·릴리즈 노트를 붙이는 화면입니다. GUI 맥락은 [Chapter 3](./03-collaboration-sourcetree.md)과 연결됩니다.

아래를 실행해 주석 태그를 만들고 목록을 확인해 보세요.

```bash
git tag -a v1.0.0 -m "First stable release"
git tag
git push origin v1.0.0
```

**예상 출력** — `git tag`만 실행했을 때 예시

```text
v1.0.0
```

**명령 해석**
- `-a`는 주석 태그, `-m`은 태그 메시지입니다.
- `git tag`만 실행하면 로컬 태그 목록이 보입니다.
- 잘못 찍은 태그는 `git tag -d v1.0.0`으로 로컬에서 지울 수 있습니다. 이미 push했다면 삭제·갱신은 팀 규칙에 맞춥니다.

이 장 범위는 CLI 브랜치 조작·병합·리베이스·태그입니다. `.git` 내부 구조는 다음 장에서, 팀 브랜치 전략 이름은 그다음 장들에서 다룹니다.

### 연습문제

**문제 1**
- 문제: fast-forward merge가 가능한 조건을 한 문장으로 쓰세요.
- 입력: 없음. 본문 8-3 표·설명을 근거로 서술
- 출력: 한쪽만 앞으로 가고 다른 쪽에 갈래 커밋이 없을 때 가능하다는 요지의 문장
- 조건: “그냥 된다”만 쓰지 말 것

**문제 2**
- 문제: 팀 규칙이 "main에는 merge commit만"일 때 rebase를 어느 브랜치에서 주로 쓰게 될지 추론하세요.
- 입력: 없음
- 출력: 아직 개인·기능 브랜치에서 `main`을 따라잡을 때라는 요지
- 조건: 본문 8-4 표·해석을 근거로 할 것

**문제 3**
- 문제: **브랜치**와 **태그**가 “가리키는 커밋” 관점에서 어떻게 다르게 움직이는지 한 문장으로 쓰세요.
- 입력: 없음
- 출력: 브랜치는 새 커밋에 따라 이동하고 태그는 한 시점에 고정된다는 요지
- 조건: 본문 8-5 기준

### 정답 포인트
- 문제 1: 받는 브랜치에 갈래 커밋이 없고 한쪽만 앞서 있으면 포인터만 앞으로 가는 fast-forward가 가능하다.
- 문제 2: `main`에는 merge로 합치고, rebase는 보통 공유 전 기능 브랜치에서 최신을 맞출 때 쓴다.
- 문제 3: 브랜치는 끝 커밋을 따라 움직이고, 태그는 특정 커밋에 이름이 고정되어 스스로 따라가지 않는다.
