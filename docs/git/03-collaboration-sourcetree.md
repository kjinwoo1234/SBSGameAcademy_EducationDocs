# Chapter 3 여러 명이 함께 Git으로 협업하기

## 학습 목표

- 원격 협업 흐름(가져오기 → 작업 → 푸시)을 반복할 수 있다.
- 브랜치를 만들고 전환해 병렬 작업을 한다.
- 병합·충돌 해결·PR까지의 역할을 설명한다.

## 본문

<a id="ch3-1"></a>

### 3-1 원격 저장소에서 협업하기

작업 전 `git pull` 또는 SourceTree의 **Pull**로 **최신 `main`을 맞춥니다.** 각자 브랜치에서 작업하면 `main`에 직접 푸시할 때 생기는 충돌을 줄일 수 있습니다. 푸시가 거절되면 보통 원격에 새 커밋이 있으므로 **먼저 가져와 병합하거나 리베이스**합니다. 리베이스 자체는 [Chapter 4](./04-multi-remote.md)에서 다룹니다.

아래 명령을 실행해 `main`을 최신으로 맞춰 보세요.

```bash
git checkout main
git pull origin main
```

예상 결과:

```text
Already up to date.
```

또는 새 커밋이 있으면 병합 요약이 출력됩니다.

**코드 해석.** `checkout main`으로 기본 브랜치에 이동한 뒤, `pull`로 원격 `main`을 가져옵니다. SourceTree에서는 같은 브랜치를 선택한 다음 **Pull**을 누르면 됩니다.

<a id="ch3-2"></a>

### 3-2 브랜치 만들고, 이동하기

브랜치 이름은 `feature/login`, `fix/typo`처럼 **목적**이 드러나게 짓습니다. `git switch -c feature/foo` 또는 `git checkout -b feature/foo`로 생성과 전환을 한 번에 합니다.

| 용어 | 의미 |
|------|------|
| 체크아웃/checkout | 특정 브랜치·커밋으로 작업 트리를 맞추는 것 |

아래 명령으로 작업 브랜치를 만들고 원격에 올려 보세요.

```bash
git switch -c feature/add-readme
git push -u origin feature/add-readme
```

예상 결과:

```text
Switched to a new branch 'feature/add-readme'
...
 * [new branch]      feature/add-readme -> feature/add-readme
```

**코드 해석.** `-c`는 브랜치를 만들며 그곳으로 이동합니다. `-u`는 이후 `git push`만으로 같은 원격 브랜치를 쓰게 합니다.

<a id="ch3-3"></a>

### 3-3 병합: 브랜치와 브랜치 합치기

**병합(merge)**은 한 브랜치의 이력을 다른 브랜치에 **합치는** 동작입니다. Fast-forward는 갈래가 없을 때 포인터만 앞으로 이동하고, 그렇지 않으면 **병합 커밋**이 생길 수 있습니다.

작업 브랜치 커밋을 `main`에 합치려면 아래 순서로 실행해 보세요.

```bash
git checkout main
git merge feature/add-readme
```

예상 결과:

```text
Updating xxxxxxx..yyyyyyy
Fast-forward
 README.md | 1 +
 1 file changed, 1 insertion(+)
```

갈래가 있으면 병합 커밋 메시지 편집 화면이 열릴 수 있습니다.

**코드 해석.** `main`으로 이동한 뒤 `merge`에 합칠 브랜치 이름을 줍니다. SourceTree에서는 `main`을 체크아웃한 뒤 대상 브랜치를 골라 **Merge**합니다.

<a id="ch3-4"></a>

### 3-4 충돌: 앗! 둘이 똑같은 코드를 고쳤어요

같은 줄을 서로 다르게 수정하면 Git이 **자동 병합에 실패**하고 충돌 마커를 남깁니다. 파일에서 `<<<<<<<`, `=======`, `>>>>>>>`를 찾아 **의도한 최종 코드**로 정리한 뒤 스테이징하고 커밋합니다.

오류 방지 패턴:

1. **언제**: 동일 라인·인접 라인을 양쪽에서 수정했을 때.
2. **왜 문제**: 잘못 고르면 빌드 오류나 로직 버그가 남는다.
3. **어떻게**: 한쪽만 남기지 말고 **실행 가능한 결과**로 수동 편집 후 `git add`와 `git commit`을 한다.

연습 저장소에서 충돌을 만든 뒤, 아래 순서로 해결해 보세요.

1. 두 브랜치에서 같은 파일의 같은 줄을 다르게 수정하고 각각 커밋합니다.
2. 한쪽으로 체크아웃한 뒤 다른 쪽을 `merge`합니다.
3. 충돌 파일이 표시되면 마커를 제거하고 최종 내용을 남깁니다.
4. `git add`로 해당 파일을 스테이징한 뒤 병합 커밋을 완료합니다.

예상 결과:

```text
병합이 완료되고, 충돌 마커가 파일에 남지 않는다.
git status에 "All conflicts fixed" 또는 커밋 완료 상태가 보인다.
```

**절차 해석.** 충돌은 실패가 아니라 **수동으로 최종본을 정하는 단계**입니다. 마커를 남긴 채 커밋하면 이후 빌드·리뷰가 막힙니다.

<a id="ch3-5"></a>

### 3-5 풀 리퀘스트: 브랜치를 합치는 예의 바른 방법

PR은 **코드 리뷰·CI 확인·토론**을 거친 뒤 병합하기 위한 절차입니다. GitHub에서 base는 보통 `main`, compare는 작업 브랜치를 선택해 PR을 엽니다. 리뷰어를 지정하고, 설명에 **변경 이유·테스트 방법**을 적는 것이 좋습니다.

아래 순서로 PR 초안을 열어 보세요.

1. 작업 브랜치를 원격에 푸시합니다.
2. GitHub 저장소에서 **Compare & pull request** 또는 **New pull request**를 엽니다.
3. base=`main`, compare=`feature/...`인지 확인합니다.
4. 제목·본문에 변경 요약과 테스트 방법을 적은 뒤 Create합니다.

예상 결과:

```text
열린 PR 페이지에 Conversation과 Files changed 탭이 보인다.
base와 compare 브랜치 이름이 의도한 것과 같다.
```

**절차 해석.** 로컬 `merge` 대신 PR을 쓰면 리뷰·CI를 거친 뒤 합칠 수 있습니다. PR 작성 습관 심화는 [Chapter 6](./06-github-features.md)에서 이어집니다.

<a id="ch3-6"></a>

### 3-6 릴리즈: 개발이 완료되었습니다. 출시하자!

**태그(tag)**는 특정 커밋에 붙는 **이름 붙은 포인터**로, 브랜치처럼 매 커밋마다 따라가지 않고 **한 시점**을 고정할 때 씁니다. 예: `v1.0.0`. GitHub **Releases**는 그 태그에 빌드 산출물·릴리즈 노트를 붙이는 화면입니다. 태그가 브랜치와 어떻게 다른지, CLI 옵션은 [Chapter 8](./08-cli-branch.md)의 **8-5**에서 이어서 다룹니다.

아래 명령으로 주석 태그를 만들고 원격에 올려 보세요.

```bash
git tag -a v1.0.0 -m "First stable release"
git push origin v1.0.0
```

예상 결과:

```text
* [new tag]         v1.0.0 -> v1.0.0
```

**코드 해석.** `-a`는 메시지와 함께 주석 태그를 만듭니다. 브랜치 푸시와 달리 태그 이름을 지정해 푸시합니다.

### 연습문제

1. 문제: 두 브랜치에서 같은 파일의 같은 함수를 수정해 충돌을 낸 뒤, 수동으로 해결하고 병합 커밋까지 완료하세요.
   - 입력: 동일 줄을 다르게 고친 두 브랜치
   - 출력: 충돌 마커 없는 최종 파일 + 병합 완료 상태
   - 조건: 자동 병합에만 의존하지 말 것

2. 문제: PR 설명에 포함하면 좋은 항목 3가지를 나열하세요.
   - 입력: 없음
   - 출력: 항목 3개. 예: 변경 요약, 스크린샷, 테스트 방법
   - 조건: Conversation에 적을 내용 기준으로 쓸 것

3. 문제: `main`을 pull로 맞춘 뒤 새 브랜치를 만들고, 커밋 1개 후 원격에 푸시하세요.
   - 입력: 연결된 `origin`
   - 출력: 원격에 새 브랜치와 커밋이 보임
   - 조건: `main`에 직접 커밋하지 말 것

### 정답 포인트

1. 협업은 최신 맞춤 + 브랜치 + PR + 병합이다. 충돌은 **의미 있는 최종 코드**로 해결한다.
2. PR 본문에는 변경 이유·범위·테스트 방법이 있으면 리뷰가 빨라진다.
3. 작업 브랜치에서 커밋·푸시한 뒤 PR로 합치는 흐름이 `main` 직접 푸시보다 안전하다.
