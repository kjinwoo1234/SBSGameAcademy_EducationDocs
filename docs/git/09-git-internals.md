# Chapter 9 Git 내부 동작 원리

## 학습 목표
- 저장소 루트의 **`.git` 디렉터리**가 하는 일과 대표 하위 항목을 말로 설명한다.
- `git add`가 만드는 객체인 블롭·트리 개념을 말로 설명한다.
- 커밋 객체가 부모·트리·메타데이터를 갖는 이유를 이해한다.
- 브랜치가 refs로 구현된다는 점을 안다.

## 본문

<a id="ch9-1"></a>
### 9-1 `.git` 디렉터리 개요

**`git init` 또는 `git clone`**을 하면 프로젝트 폴더 안에 **`.git`**이 생깁니다. 여기에 커밋·브랜치·설정 등 Git이 관리하는 메타데이터가 모입니다. **작업 디렉터리**는 `.git` **밖**에서 편집하는 소스 파일이고, **`.git` 안**은 Git 전용 데이터 영역입니다. 일반 소스는 `.git`에 직접 넣지 않습니다.

| 경로 | 역할 |
|------|------|
| `objects/` | 블롭·트리·커밋 등 객체 DB. 내용은 해시 이름 파일·팩으로 저장 |
| `refs/heads/` | 로컬 브랜치 끝이 가리키는 커밋 해시 |
| `refs/remotes/` | 원격 추적 브랜치의 커밋 해시. 예: `origin/main` |
| `HEAD` | 지금 체크아웃된 브랜치 또는 직접 커밋을 가리키는 참조 |
| `index` | 스테이징 영역. 다음 `git commit`에 넣을 스냅샷 메타데이터 |
| `config` | 이 저장소만의 설정. 원격 URL, 사용자 이름 등 |
| `hooks/` | 훅 스크립트. 커밋 전후 자동 실행 등, 선택 |

**`.git` 폴더를 지우면** 해당 폴더의 커밋 이력·브랜치 정보가 사라집니다. 작업 트리의 파일은 남을 수 있어도 Git 관점에서는 새 저장소로 다시 `git init`한 것과 같습니다. 백업 없이 삭제하지 않도록 합니다.

저장소 루트에서 아래를 실행해 `.git`이 보이는지 확인해 보세요. macOS·Linux·Git Bash 기준입니다.

```bash
ls -la .git
```

Windows PowerShell에서는 아래처럼 볼 수 있습니다.

```powershell
Get-ChildItem -Force .git
```

**명령 해석**
- `-la`와 `-Force`는 숨김 폴더 `.git`을 목록에 넣기 위한 옵션입니다.
- 출력에 `objects`, `refs`, `HEAD`가 보이면 이후 절의 구조와 연결해 읽으면 됩니다.

<a id="ch9-2"></a>
### 9-2 git add 명령의 동작 원리

`git add`는 두 가지를 합니다. 첫째, 파일 내용을 **블롭** 객체로 `.git/objects`에 저장합니다. **블롭**은 파일 내용 자체를 해시로 보관한 객체입니다. 같은 내용이면 같은 해시라 중복 저장을 줄입니다. 둘째, **인덱스**에 “다음 커밋에 넣을 스냅샷”을 기록합니다. 인덱스가 곧 스테이징 영역입니다.

폴더·파일 이름과 어떤 블롭을 가리키는지는 **트리** 객체로 표현됩니다. **트리**는 디렉터리 한 층의 목록이라고 보면 됩니다. `add` 직후에는 인덱스가 그 스냅샷을 들고 있고, `commit` 때 트리 객체로 고정됩니다.

연습 저장소에서 파일을 수정한 뒤 아래를 실행해 보세요.

```bash
git add README.md
git status
```

**예상 출력**

```text
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   README.md
```

**명령 해석**
- `git add` 후 `Changes to be committed`가 보이면 인덱스가 다음 커밋 후보를 들고 있는 상태입니다.
- 내용 자체는 블롭으로 `objects/`에 들어가고, 인덱스는 “무엇을 커밋할지”를 가리킵니다.

<a id="ch9-3"></a>
### 9-3 git commit 명령의 동작 원리

`git commit`은 인덱스에 있는 스냅샷으로 **트리**를 확정하고, 그 트리를 가리키는 **커밋** 객체를 만듭니다. **커밋**에는 트리 해시, **부모 커밋** 해시, 작성자·메시지 같은 메타데이터가 들어갑니다. 부모를 두면 커밋이 체인으로 이어져 이력이 됩니다. 첫 커밋은 부모가 없을 수 있습니다. 동시에 `main` 같은 브랜치 참조가 새 커밋 해시를 가리키도록 갱신됩니다.

스테이징이 된 상태에서 아래를 실행해 보세요.

```bash
git commit -m "Explain git objects"
```

**명령 해석**
- 새 커밋 객체가 `objects/`에 생기고, 현재 브랜치 ref가 그 해시를 가리킵니다.
- 커밋은 파일 전체를 다시 복사해 두는 폴더가 아니라, 트리·블롭·부모를 이은 **객체 그래프의 한 노드**입니다.

<a id="ch9-4"></a>
### 9-4 커밋 객체 살펴보기

방금 만든 커밋 내용을 직접 읽어 봅니다. `HEAD`는 지금 브랜치가 가리키는 커밋입니다. 아래를 실행해 보세요.

```bash
git cat-file -t HEAD
git cat-file -p HEAD
```

**예상 출력**

```text
commit
tree 4b825dc642cb6eb9a060e54bf8d69288fbee4904
parent 7e2c2f5...
author Name <mail> 1710000000 +0900
committer Name <mail> 1710000000 +0900

Commit message here
```

**명령 해석**
- `-t`는 객체 **타입**만 보여 줍니다. `HEAD`면 `commit`이 나옵니다.
- `-p`는 내용을 예쁘게 풀어 보여 줍니다.
- `tree` 줄은 프로젝트 디렉터리 스냅샷 루트입니다.
- `parent`는 직전 커밋입니다. 첫 커밋에는 없을 수 있습니다.

<a id="ch9-5"></a>
### 9-5 브랜치 작업 동작 원리

브랜치는 `.git/refs/heads/브랜치명` 파일에 **40자 해시 한 줄**을 저장하는 **참조**입니다. 참조를 줄여 **ref**라고도 부릅니다. **HEAD**는 보통 `ref: refs/heads/main`처럼 **심볼릭 참조**로 현재 브랜치를 가리킵니다. 체크아웃은 HEAD를 옮기고 작업 트리를 해당 트리로 맞춥니다.

`main`이 가리키는 해시를 확인해 보세요.

```bash
git rev-parse HEAD
cat .git/refs/heads/main
```

**예상 출력** — 두 줄이 같은 40자 해시인 경우가 많습니다.

```text
a1b2c3d4e5f6789012345678901234567890abcd
a1b2c3d4e5f6789012345678901234567890abcd
```

**명령 해석**
- `git rev-parse HEAD`는 HEAD가 최종적으로 가리키는 커밋 해시입니다.
- `refs/heads/main` 파일 내용이 그 브랜치 끝 커밋입니다.
- 새 브랜치를 만들면 보통 `refs/heads/` 아래 파일이 하나 더 생기고, 같은 해시를 가리키며 시작합니다.

이 장 범위는 `.git` 구조와 add·commit·refs의 내부 그림입니다. 팀 브랜치 전략 이름과 배포 흐름은 다음 장들에서 다룹니다.

### 연습문제

**문제 1**
- 문제: 작업 디렉터리와 `.git`의 역할을 한 문장씩으로 구분해 쓰세요.
- 입력: 없음. 본문 9-1 근거
- 출력: 작업 디렉터리 = 편집용 파일 / `.git` = 버전·참조·설정 저장 이라는 요지 두 문장
- 조건: 한쪽에만 몰아서 쓰지 말 것

**문제 2**
- 문제: `index`가 없다면 `git commit` 직전에 어떤 정보를 잃게 될지 한 줄로 추론하세요.
- 입력: 없음
- 출력: 다음 커밋에 무엇을 넣을지 스냅샷을 일관되게 기록하기 어렵다는 요지
- 조건: 본문 9-1·9-2 근거

**문제 3**
- 문제: blob, tree, commit 객체 각각이 담는 정보를 한 줄씩 정의하세요.
- 입력: 없음
- 출력: 세 줄. 블롭=파일 내용, 트리=디렉터리 목록·해시 연결, 커밋=트리+부모+메타데이터 요지
- 조건: 본문 9-2·9-3 기준

**문제 4**
- 문제: 브랜치를 새로 만들었을 때 `.git` 아래 무엇이 생기거나 바뀌는지 추론하세요.
- 입력: 없음
- 출력: `refs/heads/` 아래 새 참조 파일이 생기고 커밋 해시를 가리킨다는 요지
- 조건: 본문 9-5 기준

### 정답 포인트
- 문제 1: 작업 트리는 편집용 파일, `.git`은 버전·참조·설정의 저장소.
- 문제 2: 스테이징 없이는 다음 커밋에 넣을 스냅샷을 Git이 일관되게 쥐기 어렵다. `index`가 그 역할.
- 문제 3: blob=파일 내용, tree=디렉터리 구조와 자식 해시, commit=트리·부모·메시지 등 메타데이터.
- 문제 4: `refs/heads/새이름` 파일이 생기고 보통 현재 커밋 해시를 가리킨다.
